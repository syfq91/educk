 # 3\. `AGENTS.md` is the most important file

 Have the agent create this before writing application code.

 AGENTS.md✓

# AI Agent Development Rules

 ## Project

 This is a lightweight Android ebook reader.

 Technology:

 - Tauri 2
- Android
- TypeScript
- Rust
- foliate-js
- SQLite
- OPDS 1.2
- OPDS Progression 1.0

 Primary format:

 - EPUB

 Optional later formats:

 - PDF
- CBZ
- MOBI
- AZW3
- FB2

 The MVP is DRM-free only.

 ## Core product rule

 Books must be downloaded completely before they can be opened for reading.

 The reader must work offline after a successful download.

 Do not implement DRM.

 Do not implement ebook streaming.

 ## Architecture rules

 Keep these concerns separate:

 1. OPDS
2. Downloads
3. Local library
4. Reader
5. Reading progress
6. Progression synchronization
7. UI

 The UI must not directly implement protocol logic.

 The reader must not directly implement OPDS logic.

 The reader must not directly write SQLite.

 The OPDS client must not depend on UI components.

 The Rust layer owns native filesystem and download operations where appropriate.

 ## foliate-js

 Treat foliate-js as an external rendering engine.

 Do not fork or substantially modify it unless absolutely necessary.

 Pin the version/commit.

 Wrap foliate-js behind an application-owned Reader interface.

 Do not expose foliate-js APIs throughout the application.

 If foliate-js changes, only the adapter should normally require modification.

 ## Security

 Downloaded books are untrusted input.

 Never expose privileged Tauri APIs to ebook content.

 Never allow ebook content to access:

 - filesystem APIs
- database APIs
- Tauri commands
- application secrets
- OPDS credentials

 Ebook JavaScript must remain disabled.

 Use a restrictive Content Security Policy.

 Do not weaken security merely to make an EPUB work.

 ## Filesystem

 Store downloaded books in application-controlled storage.

 Never construct filesystem paths directly from untrusted book titles.

 Use generated IDs for storage paths.

 Never allow:

 - ../
- absolute path injection
- arbitrary filesystem access
- symlink escapes

 Use atomic downloads:

 book.tmp -\> successful validation -\> book.epub

 Never expose incomplete downloads to the reader.

 ## Database

 SQLite is the source of truth for application metadata.

 Do not store important state only in frontend memory.

 Database migrations must be versioned.

 Never delete or modify existing migrations after they have been committed.

 ## Network

 Network operations must have:

 - timeout
- cancellation where practical
- useful errors
- retry where appropriate
- offline handling

 The reader must never block on network availability.

 Reading progress is saved locally before synchronization.

 ## OPDS

 Support OPDS 1.2 initially.

 Do not add OPDS 2 unless explicitly requested.

 Support:

 - navigation feeds
- acquisition feeds
- metadata
- covers
- pagination
- MIME types
- download links
- authentication abstraction

 Do not assume every OPDS server is perfectly spec-compliant.

 Use fixtures and compatibility tests.

 ## Progression

 Implement OPDS Progression as a synchronization layer.

 Never make page navigation depend on a network request.

 Local progress is authoritative for immediate UI behavior.

 Synchronize asynchronously.

 Handle offline synchronization.

 Persist enough state to detect conflicts.

 ## Reader

 The application owns this abstraction:

 Reader

 - open()
- close()
- next()
- previous()
- goTo()
- getPosition()
- setPosition()
- setTheme()
- setFontSize()
- search() when supported
- destroy()

 Do not leak foliate-js implementation details outside the adapter.

 ## Testing

 Every feature must have tests.

 At minimum:

 - unit test
- integration test where applicable
- Android/manual test where platform behavior matters

 A feature is not complete when only the happy path works.

 Test:

 - empty states
- malformed input
- network failure
- offline mode
- cancellation
- app restart
- Android background/foreground
- corrupted downloads
- malformed EPUBs

 ## Dependencies

 Do not add dependencies casually.

 Before adding a dependency:

 1. Check whether existing code already solves the problem.
2. Check maintenance status.
3. Check license.
4. Check Android compatibility.
5. Explain why it is necessary in the PR/task report.

 ## Scope control

 Do not implement features outside the current milestone.

 Do not add:

 - DRM
- accounts
- cloud storage
- social features
- annotations synchronization
- audiobooks
- OPDS 2
- streaming

 unless explicitly requested.

 ## Completion rule

 Never report:

 "Done"

 unless:

 1. Implementation is complete.
2. Tests pass.
3. Type checking passes.
4. Lint passes.
5. Rust checks pass.
6. Android build passes when applicable.
7. Acceptance criteria pass.
8. Documentation is updated.

 If something is broken, report it honestly.

 ## Agent workflow

 Before starting a task:

 1. Read AGENTS.md.
2. Read relevant architecture documentation.
3. Inspect existing implementation.
4. Identify tests.
5. Implement the smallest correct change.
6. Run tests.
7. Run static checks.
8. Review the diff.
9. Update documentation if behavior changed.
10. Report exactly what remains.

 Never rewrite unrelated code.

 Never silently change architecture.

 Never remove tests to make a build pass.

 # 4\. Then give Claude Code a `CLAUDE.md`

 `AGENTS.md` describes engineering rules.

 `CLAUDE.md` should describe **how the agent is expected to operate**.

 CLAUDE.md✓

# Project Instructions

 You are the primary software engineering agent for this repository.

 Your job is to build the application incrementally and leave the repository in a better, working state after every task.

 ## Autonomous behavior

 You may inspect files, run commands, create files, modify code, run tests, and diagnose failures without asking for permission.

 Do not ask the user for confirmation for normal engineering decisions.

 Ask the user only when:

 - a product decision cannot reasonably be inferred
- credentials are required
- an irreversible external action is required
- two architectural choices have materially different product consequences

 Otherwise choose the simplest reasonable implementation and document the decision.

 ## Before coding

 Always:

 1. Read AGENTS.md.
2. Read docs/architecture.md if it exists.
3. Read the relevant feature documentation.
4. Inspect existing code.
5. Search for existing implementations before creating new abstractions.

 ## Work in milestones

 The project is developed in milestones.

 Never implement the entire application in one pass.

 Complete one milestone, verify it, then continue.

 ## Verification

 After implementation:

 - run relevant unit tests
- run integration tests
- run TypeScript typecheck
- run ESLint
- run Rust cargo check
- run Rust clippy
- build Android when the milestone affects Android

 If a command fails because of an environment problem, distinguish that from an application failure.

 Do not hide failures.

 ## Git discipline

 Make focused commits.

 Commit format:

 feat(scope): description\
 fix(scope): description\
 test(scope): description\
 refactor(scope): description\
 docs(scope): description\
 chore(scope): description

 Do not create giant commits covering unrelated work.

 Before committing:

 - inspect git diff
- inspect git status
- ensure no secrets are committed
- ensure generated build artifacts are excluded

 ## Architecture discipline

 Do not introduce new architectural layers unless necessary.

 Prefer:

 existing abstraction

 >

 small extension

 >

 new abstraction

 Keep the application modular but not over-engineered.

 ## Agent handoff

 At the end of a task report:

 - completed work
- files changed
- tests run
- test results
- known limitations
- recommended next task

 Do not claim success if verification is incomplete.

---

 # 24\. Critical rule for AI agents: test the risky thing first

 For this project, the risk ordering is roughly:

```
1. Can foliate-js render correctly inside Tauri Android?
                 ↓
2. Can local downloaded EPUBs be supplied safely?
                 ↓
3. Can reading position survive Android lifecycle?
                 ↓
4. Can OPDS 1.2 work against real servers?
                 ↓
5. Can Progression work reliably?
                 ↓
6. UI polish
```

 So don't let the agent spend two days building beautiful OPDS screens before proving #1.

---

 # 25\. I would also exploit an existing reference implementation

 There is already a public project describing itself as an Android/desktop reader built with **Tauri 2 + React + foliate-js**, which could be useful as a reference for practical integration patterns.  GitHub

 I would instruct the agent:

```
Search existing open-source Tauri + foliate-js ebook readers for implementation ideas.

Use them as references only.

Do not copy architecture blindly.

Check licenses before copying code.

Prefer upstream Tauri and foliate-js documentation over third-party examples.
```

 That could save a significant amount of experimentation.

 ## The ideal autonomous workflow

 Ultimately, I would have the agent operate like this:

```
READ STATUS
    ↓
READ ARCHITECTURE
    ↓
SELECT NEXT TASK
    ↓
INSPECT EXISTING CODE
    ↓
IMPLEMENT
    ↓
WRITE TESTS
    ↓
RUN TESTS
    ↓
RUN LINT / TYPECHECK / CLIPPY
    ↓
BUILD ANDROID WHEN REQUIRED
    ↓
REVIEW DIFF
    ↓
UPDATE DOCS
    ↓
UPDATE STATUS
    ↓
COMMIT
    ↓
SELECT NEXT TASK
```

 And **never**:

```
prompt
  ↓
generate 30,000 lines
  ↓
"app complete"
```

 That's the biggest difference between an AI-generated prototype and something I'd actually trust on an Android phone.

 The particularly good news is that the underlying pieces are unusually compatible: Tauri has current Android/filesystem/plugin support, foliate-js already exposes a modular reader and OPDS 1.x tooling, and the download-first constraint dramatically reduces the native complexity.  Tauri+2

 If I were actually starting this project with Claude Code, **I would make the first agent task the foliate-js-on-Tauri-Android proof of concept**, not the UI. That single experiment de-risks the most important architectural assumption before the agents build the rest of the system.
